# CCU 범위 확대와 리뷰 본문 런타임 연결

이 문서는 기존 collector와 별도의 리뷰 본문 수집·전처리 런타임을 연결하기 위한 검토 계약이다. 운영 적용 승인이나 실제 연결 완료 기록이 아니다. 기존 최근 리뷰 히스토그램과 개별 리뷰 본문 수집을 구분한다.

## 구현 및 증거 범위

기존 pinned collector/overlay의 코드와 격리 검증을 기준으로 검토한다. 일반 게임 CCU 확대는 신작 전용 planner/admission과 별도 범위다. 기존 72시간 랭킹 이탈 정책은 유지된다. CCU만 7/14/30일로 연장하는 방안은 실제 동접 랭킹 이력을 이용해 비교할 후보이며 적용값으로 확정하지 않았다.

외부 대화에서 전달된 실행 ZIP·라벨 명세·테스트 결과는 실제 파일을 확보하고 검토한 뒤 통합 근거로 사용한다. 다른 환경에서 수집한 건수나 통과한 테스트 수를 이 환경의 검증 결과로 재사용하지 않는다. 미확보한 라벨 클래스·출력 스키마·SQL을 추정해 구현하지 않는다.

이번에 추가한 `combined_budget.py`는 명시한 CCU/리뷰 페이지 상한과 다른 작업 수요를 합산하는 **오프라인 검토 도구**다. collector 실행, HTTP adapter 연결, 리뷰 적재, 장부 생성/변경, 모델 학습 또는 서비스 배포를 수행하지 않는다. `BUDGET_REVIEW_ONLY`도 운영 실행 가능 판정이 아니다.

## 수집 호스트와 공통 호출 예산

- CCU와 리뷰 수집을 같은 기존 CPU 호스트에서 실행하고 **같은 로컬 영속 SQLite 장부 파일**을 공유하는 구성을 우선 검토한다. 각 컨테이너에는 동일한 host 디렉터리를 bind mount한다. 경로 문자열·DB명·state_id만 같거나, 장부를 다른 호스트로 복사한 것은 공통 계수가 아니다. SQLite를 임의의 네트워크 파일시스템에 올리지 않는다.
- 모든 worker에 같은 readonly 정책 파일과 호환되는 예산 모듈을 전달한다. 현재 장부는 state_id/schema를 검사하지만 정책 상한 자체를 고정하지 않는다. 정책 동일성 검증의 보완 전에는 서로 다른 설정을 사용하는 worker를 연결하지 않는다.
- 리뷰 worker의 매 페이지 전송·재시도가 공통 adapter를 실제로 거쳐야 한다. 동일 DB 사용이나 라이브러리 설치만으로 계수되지 않는다. redirect는 따르지 않고, 403/429/전송 불명은 공유 차단·대기로 처리한다. 외부 전송이 불명확한 시도는 자동 환급하지 않는다.
- 전체 한도에 리뷰를 포함하면서 **리뷰 본문용 별도 cap과 기존 수집 보호 여유**가 필요하다. 기존 `NEW:*` subcap만으로 `REVIEW:*` 작업을 제한했다고 볼 수 없다. 리뷰당 건수와 HTTP 페이지 수는 다르며 수정·투표 갱신·재방문도 호출량에 포함한다.
- 한 페이지와 한 실행의 시간·페이지 수를 제한하고 기존 CCU 작업 전 양보할 수 있어야 한다. 전수 수집이 기존 wrapper lock을 계속 점유하면 안 된다. 실제 cron·lock·timeout을 대조한 뒤 실행 시간을 정한다.

GPU는 이미 실행 가능한 자원이 확인된 경우에만 사용한다. GPU에는 버전과 해시를 고정한 데이터셋을 전달하고 Steam 수집기를 추가로 띄우지 않는 구성이 최소 변경안이다. GPU나 별도 서버·유료 API가 확보됐다고 가정하지 않는다.

## 일반 CCU 확대에서 보존할 부분

1. 기존 target·작업 큐·AppID/관측 슬롯·RAW/canonical과 실제 관측 시각을 유지한다. 기존 중단 target을 일괄 재활성화하지 않는다.
2. 별도 CCU 편입/유지 정책을 명시한다. 기존 `MANUAL` 경로는 YouTube도 승격한다. 신작용 `NEW_RELEASE`는 출시 기간·보호 기간을 검사하므로 일반 게임에 그대로 재사용하지 않는다.
3. 기존 최근 리뷰 히스토그램은 active CCU/YouTube의 합집합에서 대상을 고른다. CCU 확대가 기존 리뷰의 대상·회전 주기를 바꾸는 점을 분리·검증한다. 히스토그램 작업을 개별 본문 작업으로 바꾸지 않는다.
4. CCU와 YouTube는 현재 72시간 상수를 공유한다. CCU 유지 기간의 변경은 서비스별 정책으로 분리하고 기존 `grace_until`, 재진입, 시간 순서 및 만료 처리를 검증한 뒤 적용한다.
5. 총 대상 수에는 유예 및 오류 후 재확인 대상도 포함한다. 탈락을 예상해 먼저 여유를 계산하지 않는다. 300/500/1000개 계산은 실제 편입 대상 확정이나 제공자 속도 허용을 의미하지 않는다.

## 리뷰 원본에서 학습·서비스까지의 계약

- 수집 원문은 비공개 RAW로 보존한다. 안정적인 리뷰 ID와 본문 수정 버전, 수집 시각, 원문 해시를 연결한다. 동일 본문 재수신·본문 수정·투표 수 갱신을 서로 구분한다. 각 갱신을 새로운 독립 학습 사례로 중복 집계하지 않는다.
- 전처리·분석에는 dataset/preprocessing/label/model 버전을 연결한다. 제외·보류 사유와 원본 건수, 준비된 입력 수, 분석에 포함한 리뷰 수를 별도로 기록한다. 모델 입력 준비 완료를 사람 검수 완료나 분석 성공으로 바꾸지 않는다.
- 라벨 명세와 기존 라벨링 코드가 일치하는지 확인한다. 구체적 클래스와 판단 불가/내용 없음 등의 의미는 확보한 명세를 따른다. AI가 만든 미검수 라벨을 사람 검수 정답으로 승격하지 않는다.
- 학습/시험 분할은 중복·수정 버전 간 누출을 방지하고 고정한 평가 목적에 맞게 한다. 실제 GPU 학습 및 GPT/Gemini 비교는 검수된 정답과 실행 자원이 확인된 이후 수행한다. 키·유료 호출·자원 구매를 자동으로 진행하지 않는다.
- 결과 전송은 데이터/모델/라벨 버전, 집계 분모, 원본 근거가 같은 묶음 안에서 검증돼야 한다. 재전송으로 집계를 늘리거나 오래된 결과로 최신 결과를 덮어쓰지 않는다. 새 SQL은 현재 운영 객체·최소 권한과 대조 후 비공개 변경안으로 준비한다. 완료된 DDL/GRANT/RLS/control/관리자 초기화는 반복하지 않는다.
- 서비스/RAG 연결은 같은 버전의 집계와 근거를 조회하는 별도 단계다. 현재 고정 질문형 챗봇이 실제 게임 분석을 수행하는 것처럼 표시하지 않는다. LEGAL_REVIEW는 활성화하지 않는다.

## 통합 예산 검토 도구

```text
python3 -B -m tools.collector_readiness.combined_budget --input REVIEW_PLAN.json --output UNIQUE_REVIEW_RESULT.json
```

입력은 schema_version=1의 닫힌 JSON이다. 다음 필드를 모두 명시한다. 미확인은 `null` 또는 `false`로 남기며 임의의 0이나 확인 완료로 채우지 않는다.

| 필드 | 의미 |
| --- | --- |
| `total_ccu_games` | 기존·확대·유예 대상을 포함한 동시 추적 수 |
| `interval_minutes`, `ccu_max_attempts` | 검토한 CCU 간격과 요청당 최대 전송 수 |
| `review_pages_24h`, `review_max_attempts` | 본문 수집·재방문을 포함하는 미래 페이지 cap과 최대 전송 수 |
| `other_steam_attempts_24h` | 순위·메타데이터·히스토그램·다른 실행자의 최대 전송을 반영한 수요 |
| `safety_reserve_24h`, `prior_day_debit` | 기타 여유 및 최초 장부 전환 시 이전 호출 debit |
| `rolling_day_limit` | 검토한 내부 rolling 24h 상한 |
| `minute_limit`, `minimum_interval_seconds` | 검토한 내부 전송 제한. 제공자의 보장 속도가 아님 |
| `reviewed_slot_seconds`, `non_ccu_slot_reserve_seconds` | 검토한 슬롯/실행 창과 다른 작업을 위한 예약 시간 |
| `bounded_send_duration_seconds` | 전송 간격 외 응답·처리·대기를 반영한 검토 상한. Retry-After 등으로 상한을 정하지 못하면 `null` |
| `other_consumers_accounted_for`, `shared_ledger_wiring_verified` | 다른 실행자와 동일 장부·정책·adapter 연결의 실제 확인 여부 |

검토식은 CCU `N×ceil(1440/I)×A`, 리뷰 `페이지 cap×최대 전송`, 다른 작업·여유와 이전 debit을 합산한다. 한 회차 시간은 CCU 전송 수에 내부 전송 간격과 추가 소요 상한을 보수적으로 더하고 다른 작업의 예약 시간을 반영한다. 미확인 값, 상한 초과, 시간 부족, 장부 연결 미검증은 차단 사유다. 입력을 실제로 지키는 runtime enforcement와 별도다.

## 적용 전에 필요한 증거

리뷰 원본 ZIP/명세, 실제 host·image·선택 profile·cron·lock·timeout, 읽기 전용 기존 DB 구조/권한, 최신 모든 Steam 호출량, 장부·정책 동일성, 저장 공간과 inode, 검수 데이터·GPU 실행 가능 여부가 필요하다. 각 항목은 확인한 것만 기록한다.

격리 검증은 정상 중복·본문 수정·투표 갱신·재개와 cursor 저장, RAW 보존, 사람 검수 라벨 gate, CCU/리뷰 동시 예약, 별도 cap, 403/429/timeout/장부 장애, 기존 CCU·YouTube·히스토그램 범위 보존, 재전송/구버전 결과/공개 직전 실패를 포함한다. 원본 ZIP을 검토하지 않고 이 검증을 완료했다고 보고하지 않는다.

운영 적용 전에는 변경 파일·컨테이너·서비스·DB 객체·역할·영향과 단계별 복구안을 작성한다. 기능을 끄더라도 원문·과거 관측·버전 정보와 예산 장부를 보존한다. 수집기 전체 중단, 예산 초기화, DB 전체 복원으로 우회하지 않는다.
