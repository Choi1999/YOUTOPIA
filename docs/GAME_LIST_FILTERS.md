# 게임 목록의 수집 분류와 정렬

게임 목록과 검색은 `classification`을 선택적으로 받는다. 기본 `ALL`은 분류 이력이 없는 게임도
포함한다. `GET /api/v1/games/classifications`가 현재 reader로 조회한 지원 값만 선택할 수 있다.
분류는 완료된 랭킹 수집 이력의 `(ranking_source, category_key)`이며 **공식 게임 장르가 아니다**.
분류 미지정(NULL)과 실제 범주 코드를 구분한다. 게임의 복수 소속은 허용하되 `EXISTS`로 필터링해
반복 수집/국가/기간별 관계가 결과와 전체 개수를 증식시키지 않는다. 소속은 누적 이력 기준이고,
`days=7|30`은 기존 데이터 보유 판정 기간에 적용한다. 미래 수집/미완료 원천을 포함하지 않는다.

API 식별자는 `source|category`이며 범주 NULL은 `source|`다. source/범주는 기존 원천 코드 문법과
80자 제한을 검증하고 실제 지원 목록과 대조한다. SQL에는 모두 바인딩한다. 분류 목록은128개,
목록 페이지 크기는 기존 최대100개다. 원천 없음·권한 미확인·DB 실패/타임아웃은 분류 없음이나
게임0개로 표시하지 않는다. 원천 미준비 시 전체 목록은 이용할 수 있고 선택을 전체로 복귀할 수 있다.

정렬 계약:

| 키 | 의미 | UI 기본 방향 |
|---|---|---|
| dataAvailable | 기존 기간 내 양쪽/한쪽 관측 → 과거 관측 → 확인된 관측 없음 | 고정 |
| name | 게임명, C collation | 오름차순 |
| lastObservedAt | 마지막 CCU 관측 시각 | 최신순 |
| currentCcu | 마지막 관측 CCU, 실시간 수치 아님 | 높은순 |
| peak24h | 최근24시간 관측 중 최고 CCU | 높은순 |

게임명·수치 정렬의 양방향을 유지한다. 수치0은 유효 관측이며 NULL은 항상 뒤로 보낸다.
동률은 게임명과 app_id로 고정한다. 데이터 우선은 추천/인기/트렌드 점수가 아니며 YouTube 원천이
미확인인 경우 기존 부분 판정을 유지한다. 필터→전체 결과 정렬→페이지 나누기는 서버에서 처리한다.
URL에 검색/분류/기존 필터/기간/정렬/페이지를 보존하고 조건 변경 시 페이지0으로 복귀한다.

조회 설계는 기존 reader/뷰/인덱스와 statement/transaction timeout을 유지한다. 새 캐시·요약 테이블·
물리화 뷰·운영 DDL/GRANT는 없다. count는 카탈로그와 분류 EXISTS만 사용한다.
게임명 정렬은 지표와 무관하므로 카탈로그 페이지를 먼저 고르고 그 게임의 관측 지표를 읽는다.
지표 기반 정렬은 해당 필터의 전체 후보를 평가한다. 하나의 SQL 안에서 LATERAL/기존 app_id 인덱스로
선택 후보의 canonical 관측을 읽는다. OFFSET0 경계는 canonical DISTINCT ON보다 앞에
app_id 조건을 전달할 수 있도록 해당 조회를 유지한다. 게임마다 별도 SQL을 전송하는 방식이 아니다.
최신 관측은 DISTINCT ON으로 한 행을 고르고,
기간/24시간 집계는 필요한 최근 행만 처리해 전체 이력 array_agg를 제거했다.
최신/과거 관측 판정에는 여전히 이력 조회가 필요하므로 전체 이력 접근이0이라고 주장하지 않는다.
CTE materialization은 해당 SQL 실행 중의 작업 공간이며 영속 뷰 생성이 아니다.

데이터 DB 쿼리는 전체 분류3개(count/YouTube 계약/목록), 선택 분류5개(지원 목록 검사2개 추가)로
페이지 크기와 무관하다. 선택 목록 조회는2개이며 기존 Redis 요청 예산을 사용한다. 게임별 별도
요청이나 DB 쿼리를 추가하지 않았다. 새 분류 값을 기존 제한된 이벤트 값으로 임의 수집하지 않는다.

격리 검증은360게임·144000관측·240관계에서5개 정렬×전체/선택 분류의 count/list
EXPLAIN ANALYZE, SQL 수, 실제 결과/순서를 기록한다. 데이터는 합성 어댑터이며 운영 canonical
뷰의 비용과 동일하다고 주장하지 않는다. 결과는 build/reports/game-list에 생성된다.
운영 계획은 앱 reader의 읽기 전용 EXPLAIN만 검토하며 대규모 ANALYZE/부하 시험은 하지 않는다.
작은 카탈로그의 순차 스캔을 결함으로 단정하거나 인덱스를 자동 생성하지 않는다.

최초 소개 시연의 실제 LLM 호출1회는 이전 검증이다. 이 기능의 회귀는 제공자를 모킹하며
추가 유료 호출을 하지 않는다. 운영 업데이트/키/최초 예산/최대1회 운영 수용 호출은 현재 사용자
승인 범위와 실제 서버 설정·상태를 확인하는 별도 절차다.

## Steam 태그

기존 수집 분류와 별도로 `tagId=ALL|<숫자 ID>`를 제공한다. 태그 이름은 표시용이고 필터는
양의 uint32 ID의 정규 십진 표현만 받는다. 단일 선택·전체 해제는 검색/수집 분류/기존 연결 상태/
기간/정렬과 결합하며 URL·상세 복귀 상태를 보존하고 조건 변경 시 첫 페이지로 이동한다.
태그 전체를 공식 장르라고 부르지 않는다. 활성으로 저장된 연결은 최근 수집 성공이 아니며
과거 last_seen_at이어도 활성 연결이면 포함한다. 7/30일은 기존 관측 판정 기간이다.

`GET /api/v1/games/steam-tags`는 서비스 카탈로그 게임의 실제 태그 이름/ID/언어/게임 수와
연결 및 이름의 마지막 확인 시각을 제공한다. 마지막 확인 시각은 해당 태그의 조회 가능한 활성
연결 중 최대값이며 수집 성공 시각·전체 게임의 갱신 보장이 아니다. 옵션은 최대2048개다.
누락 뷰(PENDING_CONTRACT), 권한 미확인(PERMISSION_UNCONFIRMED), 정상 빈 원천(EMPTY),
DB 오류/타임아웃을 구분한다. 선택 태그 원천을 확인하지 못하면503, 미지원 ID는400이다.
전체 해제 시에는 태그 원천 쿼리를 생략하므로 기존 목록은 계속 이용할 수 있다.

앱은 제한 계약 `service.v_game_steam_tag`의 app_id, tag_id, display_name, source_language,
link_last_seen_at, tag_last_seen_at 여섯 컬럼만 읽는다. 공급자는 기존 Steam 태그 연결과
사전의 양쪽 활성 조건 및 서비스 카탈로그 범위를 적용해야 한다. RAW 테이블 전체 권한을
요구하지 않는다. 운영 뷰/권한 변경은 별도 검토·승인 대상이며 앱 배포로 생성하지 않는다.

count/목록은 태그 관계를 EXISTS로 결합해 중복·복수 태그 소속이 게임 수를 늘리지 않는다.
태그 선택은 지원 검증2쿼리만 추가한다. 전체3, 수집 분류 또는 태그 하나 선택5, 둘 다 선택7로
페이지 크기와 무관하다. 태그 목록 자체는 계약 검사+집계2쿼리다. 기존 CCU 조회 구조·인덱스/
페이지 상한/타임아웃/요청 예산을 보존하고 새 캐시·수집·집계 정렬을 만들지 않는다.
