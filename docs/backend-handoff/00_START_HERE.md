## 1. YUTOPIA는 무엇을 하는 서비스인가요?

게임 업데이트가 진행됐을 때, YouTube 영상과 댓글에서 **어떤 반응이 관측되는지** 정리하고, 문제가 제기됐다는 사실과 실제 문제가 검증됐다는 사실을 구분한 뒤, 담당자가 검토하도록 돕는 서비스입니다.

예를 들어 사용자가 “패치 이후 성능 불만이 늘어났나요?”라고 묻더라도 서버는 댓글 개수만 보고 **패치 때문에 성능이 나빠졌다**고 답하면 안 됩니다. 수집된 댓글이 실제로 있는지, 영상 게시 날짜가 같은지, 원문이 유효한지, 자료 사용 권한이 있는지 확인해야 합니다.

현재 프론트엔드에는 **12개의 작동하는 데모 화면**이 있습니다. 하지만 이 화면들은 합성 데이터를 이용합니다. 실제 계정·YouTube API·데이터베이스·AI 서버는 **아직 연결되지 않았습니다.**

**읽기 순서(총 30~60분):**

1. **지금 보는 이 문서:** 제품 개념과 해야 할 일.

3. [02 API를 쉽게 읽는 법](./02_API_EXPLAINED.md): 화면에서 서버로 어떻게 요청을 보내는지.
4. [03 데이터 계약](./03_DATA_CONTRACT.md): 어떤 값을 어떤 의미로 저장하는지.
5. [04 상태·오류](./04_STATE_AND_ERROR_CONTRACT.md): 실패, 대기, 완료를 어떻게 구분하는지.
6. [05 보안·정책](./05_SECURITY_POLICY_CONTRACT.md): 왜 모든 데이터를 자유롭게 가져오면 안 되는지.
7. [06 테스트](./06_ACCEPTANCE_TEST_CONTRACT.md): 어떻게 정상 동작을 증명할지.

## 2. 화면 12개를 업무로 묶으면

| 화면 | 사용자에게 보이는 일 | 백엔드 개발자가 나중에 담당할 일 |
|---|---|---|
| YU-01~03 | 로그인, 선택적 YouTube 연결 | 실제 사용자 확인, 필요한 경우 채널 권한 검증 |
| YU-04 | 관측할 프로젝트 생성 | 프로젝트 저장, 입력값·소유권 검사 |
| YU-05 | 데이터 수집 진행률 확인 | 수집 Job 실행·상태·실패/재시도 관리 |
| YU-06~07 | KPI, 댓글 감성, 주요 이슈 | 정확한 집계와 출처·분모·분류 결과 제공 |
| YU-08 | 패치 전후 관측 비교 | 기간과 표본이 비교 가능한지 판정 |
| YU-09~10 | 주장과 원문 근거 검토 | 근거의 존재·삭제·만료·정책 상태·판정 기록 |
| YU-11 | 이슈 담당·검토 칸반 | 업무 상태·담당자 권한·변경 이력 저장 |
| YU-12 | AI·보고서 초안 | 허용 근거만 전달, 승인 없는 공유·내보내기 차단 |

**화면은 참고 자료이지 서버 코드가 아닙니다.** 모든 실제 서버 주소와 객체는 아직 제안 단계입니다.

## 3. 헷갈리기 쉬운 용어 12개

| 용어 | 쉬운 뜻 | 예시 |
|---|---|---|
| 프론트엔드(Frontend) | 사용자가 보는 웹 화면 | 로그인 입력창, 댓글 차트 |
| 백엔드(Backend) | 화면 뒤에서 규칙을 검사하고 데이터를 관리하는 서버 | 프로젝트 소유자 검사 |
| API | 프론트엔드가 서버에 “이 작업 해 주세요”라고 요청하는 약속 | 프로젝트 생성 요청 |
| Endpoint | 특정 일을 담당하는 API의 주소 | `POST /v1/projects` **제안 주소** |
| Request / Response | 서버에 보내는 요청 / 서버가 돌려주는 답 | 프로젝트 이름 전송 / 생성 ID 수신 |
| JSON | 데이터를 `이름: 값` 형태로 주고받는 형식 | `{"status":"QUEUED"}` |
| Schema(스키마) | 필드의 이름·타입·필수 여부를 정한 규칙 | `eventDate`는 날짜 |
| OAuth | 비밀번호를 직접 받지 않고 외부 계정의 제한된 권한을 위임받는 방법 | 채널 소유자 전용 데이터 접근 *필요 시* |
| Session(세션) | 서버가 로그인한 사용자를 확인하는 상태 | 다른 사람의 프로젝트 접근 방지 |
| Job / Worker | 시간이 오래 걸리는 작업과 실제 실행자 | 수집 요청 후 백그라운드 수집 |
| Fixture / DEMO | 화면과 테스트를 위한 가짜 고정 데이터 | NEXUS 시즌2, 댓글 12,842건 |
| Lineage(계보) | 계산 결과가 어디서 왔는지 추적 가능한 기록 | 어떤 수집 Run과 원시 응답에서 계산했는지 |

## 4. 아주 간단한 요청 흐름

```text
[사용자] 새 프로젝트 만들기 클릭
    ↓
[프론트엔드] 프로젝트 이름, 날짜, 영상 ID로 서버에 요청
    ↓
[백엔드] ① 로그인 상태 확인
           ② 이 사용자가 프로젝트 생성 권한이 있는지 확인
           ③ 날짜·중복 영상 등 입력값 검증
           ④ 저장에 성공하면 서버가 프로젝트 ID 생성
    ↓
[백엔드] 성공 응답 또는 오류 사유 전달
    ↓
[프론트엔드] 다음 화면 이동 / 입력 오류 표시
```

**중요:** 위 흐름은 앞으로 만들고자 하는 *서버 설계 제안*입니다. 현재 데모의 `ProjectDemoProvider.tsx`는 이 과정을 **브라우저 메모리에서 흉내만** 냅니다.

## 5. 세 가지를 절대로 혼동하지 마세요

**① 데이터가 0건인 것과 데이터를 가져오지 못한 것은 다릅니다.**

- `0`: 실제로 조회하고 확인했는데 0건.
- `null` + 상태 `UNAVAILABLE`/오류: 아직 모름, 실패, 권한 부족, 삭제 등.
- 서버가 모르는 수를 임의로 0건 처리하면 고객이 잘못된 결정을 합니다.

**② “댓글에서 문제가 언급됨”과 “실제 게임 결함이 검증됨”은 다릅니다.**

- `PERF-001`: 일부 댓글의 성능 저하 호소라는 **관측 후보**. 실제 결함이 입증된 것이 아닙니다.
- `PAY-002`: 과금 불만이 늘었다는 주장에 비교 가능한 근거가 없어 **HOLD(보류)**.
- 테스트용 합성 댓글을 실제 이용자 댓글로 저장·표시·외부 전송하면 안 됩니다.

**③ 작업 완료, 주장 검증, 보고서 승인은 서로 다릅니다.**

담당자가 칸반 카드를 완료했다고 그 주장이 사실이 되지 않습니다. 마찬가지로 보고서 초안이 화면에 보인다고 공개 가능한 보고서가 된 것은 아닙니다.

## 6. 개발을 시작하기 전 확인할 것

- [ ] **어느 저장소/브랜치에서 백엔드를 만들지** 관리자와 결정.
- [ ] 어떤 언어/프레임워크와 DB를 사용할지 결정. 이 문서는 **FastAPI·Node·C# 등을 확정하지 않습니다**.
- [ ] 운영 로그인 방식과 조직/프로젝트 접근 권한 결정.
- [ ] 공개 YouTube 영상 조회만 필요한지, 채널 소유자 OAuth가 필요한지 구분.
- [ ] YouTube 데이터 보관·삭제·파생·외부 전송에 대한 정책 책임자 결정.
- [ ] [02 API 해설](./02_API_EXPLAINED.md)로 하나의 요청/응답을 이해하고, 승인된 API 계약부터 테스트 작성.
- [ ] 실제 데이터를 다루기 전에 **승인되지 않은 기능은 차단(deny by default)**하도록 만들기.
- [ ] 코드를 작성할 때 [07 주석·구현 가이드](./07_BEGINNER_IMPLEMENTATION_GUIDE.md)의 규칙을 적용하기.

이 체크가 끝났다는 뜻은 **문서를 읽었다**는 것과 다릅니다. 관리자가 API 스키마와 정책 결정을 승인할 때까지 프로덕션 구현/외부 데이터 연동을 완료 처리하지 마세요.
